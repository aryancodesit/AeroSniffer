## 3. Decay Timing (Verification)

| Priority | Duration | Expected Behaviour |
|----------|----------|-------------------|
| 1 (THREAT) | 8000 ms | Creature locks on threat for 8s after last P1 event |
| 2 (touch) | 3000 ms | Watches for 3s after tap |
| 3 (flight) | 5000 ms | Watches for 5s after flight passes |
| 4 (background) | 2500 ms | Brief glance at WiFi event |

All timers reset on each same-or-higher-priority event. Preemption (lower-priority events during higher state) does not extend the higher state's deadline.

**Edge case**: If P1 arrives while in WATCHING (P2), `_decay_deadline` is set to `now + 8000`. If P2 arrives while in THREAT_LOCK, it is ignored (`pri 2 > pri 1`). If another P1 arrives during THREAT_LOCK, deadline extends by another 8000ms.

## 4. State Transition Correctness

Current `tick()` logic in `AttentionEngine.cpp:56`:

```cpp
if (_active_priority == 0 || pri <= _active_priority) {
```

This gates state transitions AND deadline updates on the priority check. For same-priority events (e.g., P2→P2), the state stays the same but deadline is extended. For lower-priority events during a higher state, nothing happens.

**Correctness verified**: The transition gate matches the spec. The only subtlety is that `_active_priority` is updated to the incoming event's priority even when the event is lower than the current state (but that can't happen because of the `pri <= _active_priority` guard).

## 5. Long-Runtime Risks (30+ Minutes)

### 5.1 — Queue Growth

The ring buffer is fixed at `QUEUE_SIZE = 16`. `_head` and `_tail` cycle within 0–15. No heap allocation occurs. Zero memory growth regardless of runtime.

**Risk: None.**

### 5.2 — Event Accumulation (Stale Events Never Drained)

**Scenario**: Device boots, no events fire for 30 minutes. Queue stays empty (`_head == _tail == 0`). `tick()` runs every ~16ms, checks `_head != _tail`, finds empty, returns. No accumulation because no events are produced.

**Scenario**: Device receives events but `tick()` never catches up. Each tick drains up to 8 events. At 60 Hz, that's 480 events/second drain capacity. Maximum realistic event rate is deauth flood — maybe 100 events/second. Queue will never persistently back up.

**Risk: None.**

### 5.3 — `_processed_count` Overflow

`_processed_count` is `uint32_t`. At max drain rate (480 events/sec), it overflows in ~104 days. Counter is debug-only, not used for control flow.

**Risk: None.**

### 5.4 — `millis()` Rollover

`_decay_deadline` is `uint32_t` milliseconds. `millis()` rolls over every ~50 days. The comparison `now >= _decay_deadline` wraps safely with unsigned arithmetic: after rollover, `now` becomes small while `_decay_deadline` is still large → condition is false → one extra decay period where no events extend the deadline. After `_decay_deadline` also rolls over ~50 days later, normal operation resumes.

**Risk: Negligible** for V2.4 use case (device reboots daily or weekly).

### 5.5 — Spinlock Starvation

`queueEvent()` uses `portENTER_CRITICAL`. If Core 0 is interrupted by a high-priority interrupt while holding the lock, Core 1's `queueEvent()` (called from touch handler) could spin-wait. However:
- `portENTER_CRITICAL` masks interrupts on the local core
- The critical section is < 20 instructions
- Worst-case spin is microseconds, not milliseconds

**Risk: None.**

### 5.6 — Volatile Cache Staleness Drift

The queue audit identified theoretical stale-read risk due to ESP32-S3's lack of hardware cache coherency. Over 30 minutes, the probability of encountering a stale read increases, but the consequence is unchanged: at most one event delayed by one frame (~16ms). No cumulative drift.

**Risk: Low.**

## 6. Option A vs Option B — Gaze Integration

### Option A: `attention_state` only (recommended for Sprint 1)

Publish only `g_creature.attention_state` from AttentionEngine. FaceEngine hardcodes gaze per state.

```
SOFT_FOCUS  → random wandering (existing logic, unchanged)
WATCHING    → anim_look_x = 0, anim_look_y = -2 (hardcoded in FaceEngine)
THREAT_LOCK → anim_look_x = 0, anim_look_y = 0 (hardcoded in FaceEngine)
```

### Option B: `attention_state + gaze_x + gaze_y`

Publish all three fields. FaceEngine reads gaze_x/y directly.

### Comparison

| Criteria | Option A (state only) | Option B (full coords) |
|----------|----------------------|----------------------|
| **Lines changed** | ~15 | ~27 |
| **Debuggability** | One variable to check: state | Three variables: state + x + y |
| **Flexibility** | Fixed gaze per state | Any gaze per state |
| **Future PC Agent gaze** | Needs FaceEngine update | Portal sends x/y directly |
| **Future emotion-specific gaze** | Needs FaceEngine update | Faces reads CreatureState directly |
| **Portal analytics** | `attention_state` transmitted | Both transmitted (more data) |
| **Risk** | Lower — hardcoded per-state gaze is simple | Higher — coordinate system errors possible |

### Recommendation

**Option A for Sprint 1.** Three reasons:

1. **One moving part.** If gaze is wrong, the cause is either (a) wrong state or (b) wrong hardcoded value. Option B adds (c) wrong coordinate publish, (d) wrong FaceEngine read, (e) signedness/range mismatch.

2. **Future flexibility.** Adding explicit gaze_x/gaze_y later is purely additive — no code deleted, no architecture changed. The migration from Option A to Option B is a 12-line diff.

3. **Portal analytics path.** `g_creature.attention_state` is what gets transmitted to Portal, not pixel offsets. The state enum (0/1/2) is what appears in logs, dashboards, and time-distribution charts. Gaze_x/y are render detail, not analytics data.
