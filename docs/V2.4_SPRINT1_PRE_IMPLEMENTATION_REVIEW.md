## Investigation 1 — EventBus Dispatch Ownership

### Finding: The internal queue is multi-producer, not single-producer

The current plan (§1.2) states the queue is "single-producer (EventBus dispatch on either core — but serialised by FreeRTOS task)". This is **incorrect**.

| Core | Publisher | Events | Context |
|------|-----------|--------|---------|
| **Core 0** | `WiFiServiceClass::connectSTA()` | WiFi CONNECTING/CONNECTED/DISCONNECTED | Normal task |
| **Core 0** | `sec_sniffer_cb()` (IRAM_ATTR) | ATTACK_DEAUTH | WiFi driver task, IRAM |
| **Core 0** | `sec_track_ap()` | ATTACK_EVILTWIN | WiFi driver task, IRAM |
| **Core 0** | `avi_fetch_flights()` | FLIGHT_DETECTED, FLIGHT_RARE | Normal task |
| **Core 1** | `pet_core1_task()` | TOUCH_SHORT | Render loop task |
| **Core 1** | `task_core1()` mode switch handler | MODE_SWITCHED | Render loop task |

Both cores call `EventBus.publish()` → synchronous callback dispatch → `AttentionEngine.queueEvent()`. Two producers, one consumer (tick on Core 1).

### Finding: `sec_sniffer_cb` is IRAM_ATTR

The security sniffer callback (`Sniffer.h:47`) is marked `static void IRAM_ATTR sec_sniffer_cb(...)`. It calls `EventBus.publish(EVENT_ATTACK_DEAUTH)`, which will call the AttentionEngine subscription lambda synchronously. While this runs in the WiFi driver task (not an ISR), the IRAM_ATTR path means `queueEvent()` should avoid flash string access or any operation that could cause a cache miss in the hot path.

### Finding: A `volatile` SPSC queue is unsafe here

With two cores writing simultaneously, a simple volatile head/tail ring buffer has a data race:

```
Core 0 reads head (=5)        Core 1 reads head (=5)
Core 0 increments head to 6   Core 1 increments head to 6
Core 0 writes data at slot 5  Core 1 writes data at slot 5
                              → ONE EVENT LOST (slot 5 overwritten)
```

`volatile` does not provide atomic read-modify-write. On Xtensa LX7, a word load/store is atomic, but `head = (head + 1) & mask` is three operations (load, add, store) that can interleave.

### Recommendation

Use a `portMUX_TYPE` spinlock to guard queue writes:

```cpp
// In AttentionEngineClass:
portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;

void queueEvent(EventType event, void* data) {
  portENTER_CRITICAL(&mux);
  // copy event, advance head
  portEXIT_CRITICAL(&mux);
}
```

The critical section is ~5 instructions (copy event type + head increment). This is safe from both core contexts and from the IRAM_ATTR callback path (it runs in a task, not an ISR).

The consumer side (`tick()`) reads the queue on Core 1 only — no mutex needed for reads.

**Risks addressed:**
- Head increment is now atomic across cores
- Event loss from competing producers eliminated
- ~10 instructions of overhead per event — negligible at < 100 events/sec

## Investigation 2 — Mode Transition Behaviour

### Finding: Active targets should NOT survive mode changes

The current plan (§3.2) has `pause()` preserving everything (queue, targets, habituation, state). This creates the following problem:

1. User is in Pet mode, a `EVENT_ATTACK_DEAUTH` fires → THREAT_LOCK
2. User switches to Security mode → `pause()` freezes the THREAT_LOCK with 6 s decay remaining
3. User stays in Security mode for 5 minutes
4. User returns to Pet mode → `resume()` continues the THREAT_LOCK
5. Creature stares at a threat that has been gone for 5 minutes

This breaks the creature's sense of presence. Attention targets are ephemeral by design (§6 of spec) — they decay in seconds, not minutes. Preserving them across mode changes undermines the decay contract.

### Finding: Habituation SHOULD survive mode changes

Habituation tracks long-term boredom patterns. If the creature habituated to NETWORK events during Pet mode, that habituation should carry forward when returning to Pet mode after a Security mode visit. Otherwise the creature "forgets" it was bored and over-reacts.

### Finding: Event queue should be flushed on pause

Events arriving during a mode pause are stale — they belong to a different mode context. Processing them on resume would create confusing behaviour (e.g., processing a WiFi event that arrived while the creature was in Aviation mode 5 minutes ago).

### Recommendation

Change `pause()`/`resume()` semantics to:

| Artefact | On Pause | On Resume |
|----------|----------|-----------|
| **Active target** | Flushed | Starts in SOFT_FOCUS |
| **Event queue** | Flushed (new events discarded) | Empty |
| **Habituation counters** | Frozen (preserved) | Windows resume sliding |
| **Gaze history buffer** | Preserved | Preserved |
| **Gaze position** | Frozen at last value in g_creature | Micro-saccades resume from last position |

```cpp
void pause() {
  if (_paused) return;          // idempotent
  _paused = true;
  clearTargets();               // flush all targets
  flushQueue();                 // discard queued events
  _paused_gaze_x = g_creature.gaze_x;  // freeze gaze display
  _paused_gaze_y = g_creature.gaze_y;
  // habituation counters are NOT touched
  // gaze history buffer is NOT touched
}

void resume() {
  if (!_paused) return;
  _paused = false;
  _state = STATE_SOFT_FOCUS;    // reset to idle
  // g_creature.gaze_x/y keep their last frozen values
  // tick() will start applying micro-saccades again
  // habituation counters resume from frozen state
}
```

This means:
- A THREAT_LOCK from 5 minutes ago never resumes — targets are ephemeral
- The creature remembers it was bored of NETWORK events (habituation survives)
- Events arriving during pause are silently discarded (they were meant for a different mode)

## Investigation 3 — Emotion Integration

### Finding: The plan prescribes THREAT_LOCK→ALERT, which is EmotionEngine's domain

Section 3.4 (and Step 8) contains:

```cpp
if (attn_state == STATE_THREAT_LOCK && attn_dur > 2000) {
    setEmotion(EMOTION_ALERT);
}
```

This is a hardcoded rule that belongs inside EmotionEngine, not prescribed by the AttentionEngine plan. The plan should define the **interface** (what context is exposed), not the **behaviour** (how EmotionEngine reacts).

### Finding: AttentionEngine's only job is providing context

Per the spec (§8.6), AttentionEngine exposes:
- `active_state` — what the creature is doing right now
- `last_target_priority` — what kind of thing it's looking at
- `target_duration_ms` — how long it's been looking
- `habituation_saturated` — whether it's bored

EmotionEngine uses this context as one input among many (timers, existing emotion, personality profile) to decide transitions. The AttentionEngine plan should not prescribe specific emotion mappings.

### Recommendation

1. **Remove the code example** from §3.4 and Step 8. Replace with an interface specification only.
2. **Remove "nudge toward ALERT" / "drift toward CALM"** language from §2.5 and §3.4.
3. **Clarify the contract**: AttentionEngine publishes context; EmotionEngine subscribes to context. The mapping between context and emotion is owned by the EmotionEngine personality system and is not part of the AttentionEngine workstream.
