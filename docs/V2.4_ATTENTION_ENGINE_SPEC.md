# AttentionEngine — V2.4 Architecture Specification

**AeroSniffer** | ESP32-S3 Multi-Boot Desk Gadget  
**Document Version:** 2.0  
**Status:** Revised

---

## 1. Purpose

### 1.1 Why AttentionEngine Exists

The AttentionEngine is the creature's visual attention system. It decides where the eyes point, what the creature notices, and how long it holds focus. Without it, the face has no orienting behaviour — the eyes would stare blankly or move at random, and the creature would appear unaware of the events happening around it.

The engine serves a single question: **"What is the creature looking at right now?"**

### 1.2 Relationship to EmotionEngine

EmotionEngine owns the creature's internal emotional state: what it feels (calm, alert, happy, etc.) and how its mood trends over time. AttentionEngine feeds EmotionEngine with real-world context — a threat lock should nudge emotion toward ALERT; a long idle gaze should let emotion drift toward CALM.

```
AttentionEngine ──gaze──► EmotionEngine
    │                        │
    │ active_state           │ uses context to filter
    │ last_priority          │ transitions
    │ target_duration_ms     │
    ▼                        ▼
 Gaze context             Emotional state
```

**V2.4 data flow is strictly unidirectional**: AttentionEngine → EmotionEngine. The return path (Emotion → Attention gaze modulation) is reserved for future work and must not be implemented in V2.4. See §10.2.

### 1.3 Relationship to FaceEngine

FaceEngine is the rendering layer — it draws pixels. AttentionEngine is a pure-logic layer — it computes gaze vectors and blink timing.

```
AttentionEngine ──► FaceEngine
    │                    │
    │ gaze_x, gaze_y     │ positions eye sprites
    │ blink_request      │ triggers blink animation
    ▼                    ▼
 Logic                 Rendering
```

FaceEngine never computes attention logic. AttentionEngine never draws pixels. FaceEngine does NOT block on AttentionEngine — if AttentionEngine has not ticked recently, FaceEngine uses the last known gaze position and assumes SOFT_FOCUS behaviour.

## 2. Responsibilities

### 2.1 Eye Gaze

Maintain a current gaze target `(x, y)` in face-relative coordinates. The gaze target is the single point the creature is looking at.

| Field | Type | Range | Description |
|-------|------|-------|-------------|
| `gaze_x` | float | [-1.0, 1.0] | Horizontal gaze, left to right |
| `gaze_y` | float | [-1.0, 1.0] | Vertical gaze, bottom to top |

Depth parameter (`gaze_z`) is reserved for future use. V2.4 ignores it; callers must treat it as 0.0.

### 2.2 Focus Targets

A focus target is anything the creature can look at. Targets are ephemeral — they exist for a duration, then expire.

| Target Source | Lifetime | Example |
|--------------|----------|---------|
| Security event | Duration of event + decay | Intrusion alert, new device probe |
| User touch | Touch duration + post-touch hold | Tap, long-press |
| Aviation event | Until next poll or timeout | Aircraft detected overhead |
| Environmental | Short-lived, single glance | WiFi connected, weather update |
| Idle (self-generated) | Infinite, regenerated on expiry | Random point on face, micro-saccade |

### 2.3 Attention Priorities

Each target carries a priority level (see §4). When multiple targets exist simultaneously, the highest-priority target wins the gaze. Lower-priority targets are suppressed but not discarded — they remain in a queue and may claim gaze once the higher-priority target decays or is dismissed.

### 2.4 Attention Decay

Attention to any non-idle target decays over time. Decay is measured in milliseconds since the target's last activity. When decay reaches a threshold, attention is released and the next target in the priority queue becomes active. If no targets remain, the engine falls back to idle behaviour (SOFT_FOCUS).

## 3. States

The AttentionEngine operates in four mutually exclusive states. Only one state is active at any moment.

### 3.1 SOFT_FOCUS

The default resting state. No external stimulus is commanding attention. The creature's gaze wanders gently with micro-saccades and occasional curiosity shifts.

| Property | Value |
|----------|-------|
| Trigger | No active target for ≥ decay period |
| Gaze behaviour | Micro-saccades within [-0.3, 0.3] range |
| Blink rate | Normal (~1 per 4–6 s) |
| Emotion influence | Allows drift toward IDLE / CALM |

### 3.2 WATCHING

The creature has noticed a stimulus and is orienting toward it. This is the entry state for all external targets.

| Property | Value |
|----------|-------|
| Trigger | New target with P2–P4 priority |
| Gaze behaviour | Smooth saccade toward target position |
| Blink rate | Normal |
| Hold time | Fixed per priority (see §6) |
| Exit | Target removed, priority superseded, or decay time reached |

### 3.3 TRACKING

Sustained attention on a target that remains active. The creature follows the target as it evolves. Eye movement is slower and more deliberate than WATCHING.

| Property | Value |
|----------|-------|
| Trigger | Target persists beyond WATCHING hold time |
| Gaze behaviour | Smooth pursuit with small corrective saccades |
| Blink rate | Reduced (~1 per 6–10 s) |
| Exit | Target removed or decay threshold reached |

### 3.4 THREAT_LOCK

Maximum attention intensity. Reserved for P1 security events. The creature fixes on the threat with minimal eye movement.

| Property | Value |
|----------|-------|
| Trigger | P1 security event |
| Gaze behaviour | Fixed stare; no micro-saccades |
| Blink rate | Minimal (~1 per 12–20 s) |
| Emotion influence | Forces EmotionEngine toward ALERT |
| Exit | Security event resolved or explicit override via higher-priority stimulus (touch) |

### State Transitions

```
                  ┌──────────────┐
                  │  SOFT_FOCUS  │◄──────────────────────────┐
                  └──────┬───────┘                          │
                         │ target arrives                   │
                         ▼                                  │
                  ┌──────────────┐                          │
         ┌───────►│   WATCHING   ├──────── decay ───────────┘
         │        └──────┬───────┘
         │               │ target persists
         │               ▼
         │        ┌──────────────┐
         │        │   TRACKING    ├──── decay ───────────────► SOFT_FOCUS
         │        └──────┬───────┘
         │               │ P1 event
         │               ▼
         │        ┌──────────────┐
         │        │ THREAT_LOCK  ├──── event resolved ──────► SOFT_FOCUS
         │        └──────┬───────┘
         │               │ user touch (P2)
         └───────────────┘
```

## 4. Priority System

All attention targets are assigned a priority level. The active target is always the highest-priority non-expired target.

### Levels

| Level | Label | Sources | Preempts | Preemptable By |
|-------|-------|---------|----------|----------------|
| P1 | Security | EVENT_INTRUSION, new station probe | All | P1 (higher-severity security only) |
| P2 | User Touch | Touch tap, touch long-press | P3–P5, P1 under decay | P1 |
| P3 | Aviation | EVENT_FLIGHT_DETECTED, EVENT_FLIGHT_RARE | P4–P5 | P1–P2 |
| P4 | Environment | WiFi connect/disconnect, weather update, heartbeat, timeline events | P5 | P1–P3 |
| P5 | Idle | Self-generated micro-saccades, random curiosity looks, breathing animation | None | All |

### Priority Rules

1. **Preemption**: When a higher-priority target arrives, it immediately claims gaze. The preempted target remains queued and resumes if its priority slot becomes available again before its decay expires.

2. **Supression**: Multiple targets at the same priority level are resolved by most-recent-first. The most recently arrived target claims gaze; older targets at the same level are queued.

3. **P1 stacking**: If a P1 target is active and a second P1 target arrives (e.g., two stations probe simultaneously), the newer target replaces the current. The previous P1 target is discarded — only the most recent security event holds attention.

4. **Touch override**: A P2 touch event preempts P1 only if the P1 target has already exceeded 50 % of its decay threshold. This prevents the creature from ignoring a fresh threat when the user taps.

### Worked Example

```
Time  │ Event                              │ Active Target  │ State
──────┼─────────────────────────────────────┼────────────────┼─────────────
0     │ Boot, no events                    │ Idle           │ SOFT_FOCUS
5     │ WiFi connects (P4)                 │ WiFi icon      │ WATCHING
7     │ User tap (P2)                      │ Touch location │ WATCHING
8     │ Intrusion alert (P1)               │ Threat         │ THREAT_LOCK
12    │ Intrusion resolved, P1 decays      │ Touch location │ WATCHING (resume)
14    │ Touch expires, P2 decays           │ WiFi icon      │ WATCHING (resume)
19    │ WiFi attention expires             │ Idle           │ SOFT_FOCUS
```

## 5. Gaze Behaviours

### 5.1 Micro-saccades

In SOFT_FOCUS, the gaze drifts continuously with small-amplitude shifts.

| Parameter | Value | Notes |
|-----------|-------|-------|
| Amplitude | [0.01, 0.08] | In face-relative units |
| Interval | 200–600 ms | Poisson-distributed |
| Direction | Random uniform | No directional bias |
| Movement | `gaze += noise(amplitude) * delta_t` | Integrated over tick delta; no explicit waveform |

The engine updates gaze position by adding noise scaled by the tick interval. This produces smooth drift without committing to sub-100 ms waveforms that the scheduler cannot reliably deliver.

These are purely cosmetic — they prevent the "dead eye" look when nothing is happening.

### 5.2 Long Stares

During TRACKING or THREAT_LOCK, the creature holds gaze on a point for extended periods.

| State | Hold Duration | Movement |
|-------|---------------|----------|
| WATCHING | 0.8–2.0 s | Single saccade to target, then hold |
| TRACKING | 3–8 s | Slow drift within 0.05 radius of target |
| THREAT_LOCK | 5–20 s | Nearly frozen; < 0.01 drift |

### 5.3 Curiosity Looks

When a P3 or P4 target arrives, the creature performs a quick orienting saccade toward the direction of the event, then returns to its previous focus if the event does not escalate.

```
Curiosity look sequence:
  1. Hold current gaze (100 ms)
  2. Fast saccade toward event direction (50–80 ms)
  3. Hold on event (400–800 ms)
  4. Saccade back to previous target (50–80 ms)
```

The "back" saccade only occurs if the previous target still has remaining attention time. If the previous target has expired, the curiosity look becomes a full WATCHING entry for the new target.

### 5.4 Threat Lock

During THREAT_LOCK, all non-essential eye movement is suppressed.

| Behaviour | During Threat Lock |
|-----------|-------------------|
| Micro-saccades | Disabled |
| Blink rate | Reduced to minimum |
| Curiosity looks | Suppressed (P1 > P3/P4) |
| Touch override | Allowed only if P1 is past 50 % decay |
| Emotion output | Forces EmotionEngine toward ALERT |

The threat lock releases immediately when the triggering P1 event is dismissed. It decays naturally if no new P1 events arrive, following the P1 decay schedule.

## 6. Attention Decay Rules

Every non-idle target has a decay timer. Decay begins when the target is first created. If decay elapses without any renewal event, the target expires and is removed from the attention queue.

### Decay Timers by Priority

| Priority | Decay Time | Notes |
|----------|-----------|-------|
| P1 Security | 8 s | Extended to 15 s if no user touch intervenes |
| P2 Touch | 3 s after release | Touch active → hold; release → decay |
| P3 Aviation | 5 s | Per aircraft detection event |
| P4 Environment | 2.5 s | WiFi, weather, heartbeat timeline events |

### Decay Mechanics

1. Every `tick()` call decrements the active target's remaining time by `delta_ms`.
2. When remaining time reaches 0, the target expires.
3. The engine checks the priority queue for the next-highest target with remaining time > 0.
4. If no targets remain, the engine transitions to SOFT_FOCUS.
5. If a preempted target still has remaining time, it becomes active when all higher-priority targets expire.

### Decay Renewal

A target's decay is renewed (reset to full) when:

- Same-type event occurs while the target is active (e.g., second aircraft detected during P3 window)
- User touch during P1 decay: resets P1 decay timer (user engagement extends threat awareness)

A target's decay is NOT renewed by:

- Higher-priority preemption (the preempted target's timer continues running)
- Idle gaze (SOFT_FOCUS does not renew any target)

## 7. Habituation Rules

Habituation prevents the creature from over-reacting to repetitive, low-significance stimuli. Without habituation, a device that probes every 5 seconds would keep the creature in a perpetual WATCHING state.

### Habituation Categories

| Category | Sources | Habituation Window | Max Responses |
|----------|---------|-------------------|---------------|
| NETWORK | WiFi connect/disconnect, station probe | 60 s | 2 |
| AVIATION | Aircraft detected | 120 s | 1 |
| TOUCH | Tap | 10 s | 3 |
| SYSTEM | Heartbeat, mode transit, timeline events | 30 s | 2 |

### Response Accounting

The habituation counter increments when the engine **evaluates** an event for attention, not when it ultimately displays the gaze shift. An event that arrives during a higher-priority preempt still counts toward habituation even if the creature never visibly looks at it. This prevents a subtle exploit where rapid P1 events could mask P3/P4 habituation resets.

### Rules

1. **Per-category counter**: Each category tracks how many times the creature has responded to events in the current habituation window. Counter increments at event evaluation time, not gaze-display time.

2. **Suppression**: When the category counter exceeds `Max Responses`, all subsequent events in that category are logged but do NOT create attention targets. The creature appears to "ignore" them.

3. **Window reset**: The habituation window slides — it is measured from the FIRST event in the category. When `now - window_start > habituation_window`, the counter resets to 0.

4. **Priority override**: Habituation does NOT apply to P1 (Security) events. Security events always create attention targets regardless of recent frequency.

5. **Threat sensitization**: After a P1 THREAT_LOCK resolves, all habituation counters are halved (rounded down). This makes the creature temporarily more reactive to all stimuli — it is "on edge" after a threat. Sensitization decays linearly over 30 s back to normal levels.

6. **Escalation exception**: If an event's internal metadata signals escalation (e.g., RSSI above threshold for a station probe), the habituation counter is ignored and the event creates a full attention target. This prevents the creature from ignoring a genuinely close-range device because it has habituated to distant probes.

### Cross-Category Independence

Habituation categories are independent. Habituating to NETWORK does not affect AVIATION, TOUCH, or SYSTEM responsiveness. The creature can be bored of WiFi but still react to an aircraft.

### Habituation State

The engine exposes a read-only snapshot of habituation state for debugging and UI:

```text
NETWORK: 2/2 (window ends in 34 s)
AVIATION: 1/1 (window ends in 92 s)
TOUCH: 1/3
SYSTEM: 0/2
SENSITIZED: 18 s remaining
```

## 8. Integration Points

### 8.1 Runtime Ownership

The AttentionEngine is a **singleton service** owned by the OS layer (`AeroSnifferOS`), declared alongside `EmotionEngine`, `WiFiServiceClass`, `FaceEngineClass`, and `StorageServiceClass`. A single global instance is accessible via `extern` declaration.

```text
// AeroSnifferOS.h — singleton declaration
extern AttentionEngineClass AttentionEngine;
```

The engine has no dynamic allocation, no heap dependency, and no movable or copyable semantics. It is constructed at compile time and initialized at runtime via `begin()`.

### 8.2 Lifecycle

| Phase | Call | When | What Happens |
|-------|------|------|-------------|
| Init | `AttentionEngine.begin()` | `setup()`, after EmotionEngine.begin() | Initialises internal state, allocates no heap, subscribes to EventBus |
| Tick | `AttentionEngine.tick(delta_ms)` | Every iteration of the Core 1 render loop, before EmotionEngine.tick() | Processes queued EventBus events, decays active target, updates gaze position, handles state transitions |
| Teardown | `AttentionEngine.end()` | On mode transition (teardown) | Clears attention queue, resets habituation counters, unsubscribes from EventBus |
| Mode setup | `AttentionEngine.reset()` | On mode transition (setup) | Clears queue, keeps habituation state, returns to SOFT_FOCUS |

### 8.3 Tick Source and Core Affinity

```
Tick source:   Core 1 render loop (task_core1), called every iteration
Tick order:    EventBus.process() → AttentionEngine.tick() → EmotionEngine.tick() → FaceEngine.render()
Core affinity: Core 1 (UI/render core). NOT called from Core 0.
```

The engine is ticked from Core 1's render loop to keep gaze updates synchronized with the display frame. It is NOT called from Core 0's background task to avoid concurrent state mutation.

### 8.4 Thread Safety

EventBus events can arrive from either core. The engine handles this by:

1. **Event queuing**: The engine does NOT subscribe to EventBus callbacks directly. Instead, EventBus events that affect attention are copied into a small lock-free queue inside the engine.
2. **Deferred processing**: The queue is drained during `tick()` on Core 1. This ensures all attention state mutations happen on a single core.
3. **No mutexes**: The engine holds no mutexes. Event producers on Core 0 write to the queue via a single-producer pattern (EventBus dispatch on Core 0 is serialised by the FreeRTOS task structure). The queue is read-only from Core 1.
4. **Stall recovery**: If `tick()` has not been called for 1000 ms or longer (e.g., Core 1 is blocked), the engine reads a single timestamp from `millis()` on the next tick and applies the delta in one pass. Gaze position is extrapolated but state transitions may be compressed. This is soft-failure — the creature may appear briefly frozen, then catch up.

### 8.5 EventBus

The AttentionEngine subscribes to these EventBus events:

| Event | Effect | Priority |
|-------|--------|----------|
| `EVENT_WIFI_CONNECTED` | Curiosity look toward network status | P4 |
| `EVENT_WIFI_DISCONNECTED` | Curiosity look | P4 |
| `EVENT_WIFI_CONNECTING` | Brief glance (subsumed by CONNECTED/DISCONNECTED) | P4 |
| `EVENT_FLIGHT_DETECTED` | WATCHING/TRACKING for aircraft | P3 |
| `EVENT_FLIGHT_RARE` | Extended WATCHING (renewed decay) | P3 |
| `EVENT_INTRUSION` | THREAT_LOCK | P1 |
| `EVENT_TOUCH_SHORT` | WATCHING touch point | P2 |
| `EVENT_TOUCH_LONG` | Extended WATCHING touch point | P2 |
| `EVENT_MODE_CHANGED` | Curiosity look (new mode name) | P4 |
| `EVENT_TIMELINE` | Soft glance for high-significance timeline events | P4 |

### 8.6 EmotionEngine

AttentionEngine communicates gaze activity to EmotionEngine through a lightweight interface:

```
AttentionEngine → EmotionEngine:
  - active_state: SOFT_FOCUS | WATCHING | TRACKING | THREAT_LOCK
  - last_target_priority: P1–P5
  - target_duration_ms: how long current target has been active
  - habituation_saturated: bool (is the creature bored of current category?)
```

EmotionEngine uses this to:

- Escalate toward ALERT during sustained THREAT_LOCK
- Drift toward CALM during extended SOFT_FOCUS
- Subdue emotional response during habituation saturation (the creature is "used to" the stimulus)
- Trigger rare emotions (SURPRISED) on first-in-window P3/P4 events

### 8.7 FaceEngine

AttentionEngine provides FaceEngine with per-frame rendering parameters:

```
AttentionEngine → FaceEngine each frame:
  - gaze_x: float [-1.0, 1.0] — horizontal eye position
  - gaze_y: float [-1.0, 1.0] — vertical eye position
  - blink_request: bool — trigger a blink cycle
```

FaceEngine handles its own blink timing and animation. AttentionEngine only signals *when* to blink based on the active state's blink rate. FaceEngine may ignore `blink_request` if it is mid-blink.

V2.4 FaceEngine does not receive pupil scale, saccade velocity, or blink urgency parameters. Those outputs are reserved for Sprint 2+ and must not be implemented in the first integration.

## 9. Constraints

### 9.1 No Camera

The AttentionEngine has no vision system. It does not sense the physical environment optically. All attention targets are derived from software events (WiFi, serial, touch sensor, internal timers). The creature cannot see the user's face, gestures, or surrounding objects.

This constraint is deliberate — it forces attention to be chemically emergent from system state rather than optically reactive.

### 9.2 No Cloud

All attention logic runs locally on the ESP32-S3. No attention state, gaze history, or habituation data is sent to or retrieved from external servers. The engine is fully air-gapped by design.

### 9.3 No Additional Hardware

The AttentionEngine uses only peripherals already present in the DeskBuddy 2.0 hardware:

- Capacitive touch sensor (GPIO 43)
- WiFi radio (station + promiscuous mode)
- Serial UART (companion app communication)
- FreeRTOS timers (millis() for decay and habituation windows)

No camera, no IMU, no PIR sensor, no external RAM.

## 10. Future Expansion Hooks

V2.4 exposes exactly one forward-looking stub. All other speculative interfaces (camera, cloud personality, multi-sensor fusion) are out of scope and must not be defined, reserved, or discussed in the V2.4 codebase.

### 10.1 Gaze History Logging

The engine MAY record the last 64 gaze targets with timestamps in a circular RAM buffer for debugging and post-hoc analysis.

```text
struct AttentionRecord {
    uint32_t timestamp_ms;
    uint8_t  state;      // SOFT_FOCUS | WATCHING | TRACKING | THREAT_LOCK
    uint8_t  priority;   // P1–P5
    uint8_t  category;   // NETWORK | AVIATION | TOUCH | SYSTEM | IDLE
};
```

The buffer is never flushed to SPIFFS in V2.4. It lives in RAM and is lost on reset. Future work MAY add optional SPIFFS logging for post-mortem analysis.

### 10.2 Emotional Gaze Modulation (Reserved)

The reverse path (EmotionEngine → AttentionEngine) is reserved for a future Sprint. V2.4 implementers MUST NOT add any code that reads EmotionEngine state to modulate gaze parameters. The design intent is documented here for continuity:

| Emotion | Intended Gaze Effect |
|---------|---------------------|
| HAPPY   | Faster saccades, wider micro-saccade amplitude |
| SAD     | Slower saccades, downward gaze bias (-0.1 y offset) |
| ALERT   | Narrower micro-saccades, quicker threat lock entry |
| ANGRY   | Longer stare holds, reduced blink rate |
| SURPRISED | Single large saccade, then return to prior target |

This table is informational only — it constrains future architecture decisions and prevents incompatible EmotionEngine changes. It is not an implementation task.

## 11. Error and Stall Recovery

### 11.1 Tick Stall

If `tick()` has not been called for 1000 ms or longer, the engine detects this on the next call by comparing `millis()` against the last tick timestamp. It applies the full delta in one pass:

- Targets decay by the full missed interval
- Gaze position drifts via a single scaled noise step (no sub-frame interpolation)
- Habituation windows slide by the missed interval
- State transitions that would have occurred during the stall are applied immediately

The creature may appear frozen during the stall and then snap to a new gaze position on recovery. This is acceptable for V2.4.

### 11.2 Event Queue Overflow

The internal event queue has a fixed capacity of 16 entries. If the queue is full when a new event arrives, the oldest unprocessed event is dropped. The new event is always accepted. This prevents a burst of events from permanently starving the engine.

### 11.3 Mode Transition

On mode transition, `reset()` is called:

- All queued and active targets are cleared (including P1)
- Habituation counters are preserved (the creature remembers it was bored of WiFi in the previous mode)
- State returns to SOFT_FOCUS
- Gaze resets to centre (0, 0)
