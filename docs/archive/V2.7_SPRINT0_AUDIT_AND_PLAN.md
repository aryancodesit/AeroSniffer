## 1. Executive Summary

AeroSniffer V2.6 delivered a certified Release Engineering pipeline (GitHub Actions, evidence framework, signature matcher, provider architecture). The repository is functional and the firmware compiles cleanly.

However, a post-release audit reveals significant technical debt accumulated across V2.4–V2.6:

- **~178 MB of build artifacts** tracked in git
- **3 overlapping bug-tracking files** with inconsistent content
- **2 copies of pc_agent.py** (legacy + modern), one with outdated face protocol
- **47 files in docs/**, many stale or contradictory
- **4 root-level planning docs** referencing pre-V2.6 milestones
- **Production serial debug logging** emitting raw sensor values and transition traces
- **No single-owner serial architecture** — 3 code paths contend for COM port access
- **Bug BUG-007 (Typing Emotion Stuck)** remains open, with known root cause

Sprint 0 is a hygiene sprint. It should not introduce new features. It removes dead weight, resolves the serial contention problem architecturally, and consolidates documentation to a single source of truth.

## 7. Serial Communication Bridge Architecture

### 7.1 Current Problem

Three independent code paths contend for the ESP32's single USB CDC serial port:

```
┌──────────────┐     ┌───────────────┐
│  pc_agent.py ├────►│               │
│  (direct)    │     │   ESP32 USB   │
├──────────────┤     │   CDC Serial  │
│  serial_     ├────►│   (COM port)  │
│  daemon.py   │     │   115200 8N1  │
├──────────────┤     │               │
│  companion-  ├────►│               │
│  app (Web    │     │               │
│  Serial API) │     └───────────────┘
└──────────────┘
```

**Problems:**
1. Only one process can open the COM port at a time
2. `pc_agent.py` connects directly AND there's a `serial_daemon.py` — they conflict
3. Web companion (`serial.ts`) attempts browser Web Serial, which disconnects USB from OS drivers
4. No message routing — all traffic shares one line with no addressing
5. No backpressure or flow control for high-throughput data (e.g., telemetry at 2 Hz)

### 7.2 Proposed Architecture: Serial Bridge Service

```
┌──────────────┐     ┌──────────────────┐     ┌──────────────────────┐
│  ESP32 Firmware├────►│  Serial Bridge   │◄────┤  pc_agent.py        │
│  (USB CDC)    │     │  Service         │     │  (emits events,      │
│               │     │                  │     │   no direct FACE:    │
│               │     │  - COM port owner│     │   commands)          │
│               │     │  - Message router│     └──────────────────────┘
│               │     │  - Protocol      │     ┌──────────────────────┐
│               │     │    multiplexer   │◄────┤  companion-app       │
│               │     │  - TCP server:   │     │  (WebSocket/HTTP     │
│               │     │    127.0.0.1:    │     │   to bridge)         │
│               │     │    12345         │     └──────────────────────┘
│               │     │  - WebSocket:    │     ┌──────────────────────┐
│               │     │    :12346        │◄────┤  CLI tools           │
│               │     │  - Message queue │     │  (send.py, scripts)  │
│               │     │  - Health check  │     └──────────────────────┘
│               │     │  - Auto-reconnect│
└──────────────┘     └──────────────────┘
```

### 7.3 Protocol Changes

**ESP32 → Bridge (serial):**
```
RES:{...}    — JSON response to command
EVT:{...}    — Unsolicited event (timeline, threat, flight)
TEL:{...}    — Telemetry (cpu, ram, heap, uptime)
PONG         — Health check response
```

**Bridge → ESP32 (serial):**
```
CMD:{...}    — JSON-wrapped command with message ID
PING         — Health check
```

**TCP/WebSocket clients → Bridge:**
```
JSON messages with addressing:
{"to":"esp32","cmd":"set_face","face":"happy","id":1}
{"to":"esp32","cmd":"set_status","text":"Hello"}
{"to":"all","type":"subscribe","events":["threat","flight"]}
```

### 7.4 Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| JSON-only on serial (no raw FACE:/STATUS:/APP:) | Unifies protocol; C++ JSON parsing already present (ArduinoJson) |
| Bridge owns the COM port exclusively | Eliminates contention |
| TCP + WebSocket dual transport | TCP for local tools, WS for web companion |
| Message IDs for request-response | Enables at-most-once delivery semantics |
| Event subscriptions | Clients subscribe to event types rather than polling |
| Aggregation layer in bridge | Bridge can buffer, deduplicate, and throttle ESP32-bound messages |

### 7.5 Migration Path

1. **Phase 1 (Sprint 0):** Rename `serial_daemon.py` to `serial_bridge.py`. Extend to support WebSocket. Make `pc_agent.py` connect through the bridge instead of directly.
2. **Phase 2 (Sprint 1+):** Move serial protocol to JSON-only. Update companion-app `serial.ts` to connect via bridge WebSocket.
3. **Phase 3 (Future):** Optional — expose bridge as a Windows service / systemd unit for auto-start.

### 7.6 Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| JSON parsing on ESP32 adds latency | Medium | ArduinoJson is already a dependency; streaming parser for large payloads |
| Bridge becomes a single point of failure | Medium | Auto-restart via daemon; ESP32 falls back to standalone operation |
| Breaking FACE:/STATUS:/APP: protocol breaks existing clients | High | Backward-compatible bridge: accepts both raw and JSON during transition |
| WebSocket adds Python dependency | Low | `websockets` library is pure Python, no native deps |

## 8. Wireless-First Workflow Assessment

### 8.1 Current State

AeroSniffer already operates wirelessly for its web dashboard:
- WiFi SoftAP + Station mode
- REST API on port 80 (Security Portal)
- WebSocket streaming for events

However, the **PC Agent** still requires USB serial:
- No wireless bridge for PC events
- Companion app connects via serial or direct USB
- No WiFi-based telemetry streaming to companion app

### 8.2 Gap Analysis

| Capability | Status | Note |
|------------|--------|------|
| WiFi AP | ✅ Working | Security mode Portal |
| WiFi STA | ✅ Working | Aviation mode OpenSky |
| REST API | ✅ Working | Portal v2 settings/devices/threats |
| WebSocket | ✅ Working | Event streaming in Portal |
| PC Agent over WiFi | ❌ Missing | Still USB-only |
| Companion app over WiFi | ❌ Missing | Web serial only |
| Telemetry streaming | ❌ Missing | No real-time push to companion |
| MQTT / Home Assistant | ❌ Not implemented | Future scope |

### 8.3 Recommendation

The serial bridge (Section 7) enables wireless PC Agent operation:
- PC Agent connects to bridge via TCP (localhost) or WebSocket
- Bridge forwards to ESP32 via serial
- No architectural change needed on ESP32 — it still talks serial
- Companion app can connect via bridge WebSocket instead of Web Serial API

This is a **zero-firmware-change** path to wireless-first operation.

**Description:** Investigate and fix the Typing Emotion Stuck bug. Root cause is known: PC Agent emits `FACE:THINKING` directly, and the firmware has no inactivity timeout for externally-set faces.

- In `Mode1_Pet.h` `pet_core1_task()`: add a timeout for serial-driven faces

**Files modified:**
- `Mode1_Pet.h` — add `last_serial_ms` tracker + time-out fallback

**Risk:** Low. Timeout only triggers when serial is genuinely silent.

**Acceptance:** After 60s of no serial commands, face returns to IDLE. Normal operation unaffected.
