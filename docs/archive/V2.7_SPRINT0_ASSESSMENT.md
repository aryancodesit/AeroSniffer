## Sprint 1 Architecture

### Current (V2.6)

```
Observe → Attention → Emotion → Mood → Face
                                          ↑
                                     Persistence (observer)
                                     Memory (observer, 4 domains)
```

Memory is an observer with no consumer. It records and decays but nothing reads it.

### Target (V2.7 Sprint 1)

```
Observe → Attention → Emotion → Mood → Face
                                          ↑
                                     Persistence (observer)
                                     Memory → Behavior Layer → CreatureState
```

**New component: Behavior Layer**

| Property | Design |
|----------|--------|
| What it is | A single `BehaviorEngineClass` in the tick loop, positioned after MemoryEngine |
| What it reads | `MemoryEngine.recall()` — memory summary with domain strengths and top records |
| What it writes | `CreatureState` — specifically `mood`, `mood_strength`, `engagement_drive`, and new `behavior_ctx` field |
| What it does NOT write | FaceEngine, EmotionEngine, AttentionEngine, MemoryEngine |
| Tick position | `MemoryEngine.tick()` → `BehaviorEngine.tick()` → `FaceEngine.updateAnimations()` |
| When it runs | Core 1, after Memory tick, before Face render |
| Decision model | Deterministic rules based on memory domain strengths and recent event recency — no ML, no randomness |
| Initial scope | Use recency-weighted domain strengths to bias mood toward ALERT (recent threat/flight events) or CALM (prolonged quiet), and modulate engagement_drive recovery when significant events are fresh |
| Explicity excluded | Learned preferences, personality evolution, predictive modeling — these require a stable behavior layer first |

### Why Not Memory → Face Directly

Connecting MemoryEngine to FaceEngine directly would violate three embedded systems principles:

| Principle | Violation |
|-----------|-----------|
| **Single responsibility** | FaceEngine renders. If it also interprets memory, it now has two reasons to change (rendering logic + behavioral logic). |
| **Separation of concerns** | MemoryEngine is an observer with no awareness of rendering. It should not be coupled to FaceEngine's data model. |
| **Testability** | A Behavior Layer can be unit-tested in isolation. Testing memory-informed rendering requires hardware. |

The Behavior Layer acts as an **adapter** between memory (raw domain strengths, event recency) and creature state (mood, engagement, attention bias). It translates one domain model to another without coupling the two.

### Behavior Layer V1 Rules (Proposed)

```
For each tick:
  summary = MemoryEngine.recall()
  if summary.domain_strength[SECURITY] > 30 and
     summary.domain_strength[SECURITY] > summary.domain_strength[MOOD]:
       // Recent threat activity → elevate alertness
       engagement_drive = max(engagement_drive, 60)  // floor at alert
       mood_strength_override = MOOD_ANXIOUS influence

  if summary.domain_strength[AVIATION] > 20 and
     recent_flight_event (last 60s):
       // Recent flight spotting → mild curiosity
       attention_bias = TARGET_FLIGHT tendency

  if summary.domain_strength[TOUCH] > 25:
       // Recent interaction → reinforce current mood
       mood_strength += 5 (capped at 100)

  if no significant memory activity for > 120s:
       // Quiet → allow natural mood decay
       no override
```

These rules are deterministic, additive, and trivially testable. They produce observable behavioral change (creature becomes alert after security events) without touching rendering code.

## Architectural Decision Record

### Decision: Behavior Layer as independent engine

**Context:** V2.6 Memory Engine records and decays events across 4 domains (Touch, Security, Aviation, Mood) but has no consumer. The creature cannot act on what it remembers.

**Options considered:**
1. **MemoryEngine writes CreatureState directly** — violation of separation of concerns, couples memory format to creature state
2. **FaceEngine reads MemoryEngine directly** — couples renderer to raw memory, violates single responsibility
3. **Behavior Layer mediates between Memory and CreatureState** — additive, testable, preserves all existing boundaries

**Chosen:** Option 3. Behavior Layer is a new engine that reads MemoryEngine output via the existing `recall()` API and updates CreatureState fields that other engines already consume (mood, engagement_drive).

**Consequence:** FaceEngine remains a pure renderer. It has no awareness of MemoryEngine. The Behavior Layer can be tested in isolation, replaced, or extended without touching rendering or memory code.

**Explicitly deferred:**
- Learned preferences (requires behavior stability first)
- Predictive or ML-based behavior (vision for V3)
- Multi-drive behavior model (curiosity, fatigue, exploration — future version)

## Assessment

### Separation of Concerns

The V2.6 architecture has a gap: Memory observes but nothing acts on it. The Behavior Layer closes this gap without violating existing boundaries. Each engine has exactly one job:

| Engine | Reads | Writes |
|--------|-------|--------|
| AttentionEngine | Touch, EventBus | `CreatureState.attention` |
| EmotionEngine | `CreatureState.attention` | `CreatureState.emotion` |
| MoodEngine | `CreatureState.attention`, `CreatureState.emotion`, touch history | `CreatureState.mood`, `CreatureState.mood_strength` |
| MemoryEngine | Touch, Security, Aviation events | LittleFS, internal ring buffer |
| BehaviorEngine | `MemoryEngine.recall()` | `CreatureState.mood`, `CreatureState.mood_strength`, `CreatureState.engagement_drive` |
| FaceEngine | `CreatureState` (all fields) | TFT display buffer |
| PersistenceService | `CreatureState.attention`, `CreatureState.mood` | NVS |

The data flow is unidirectional and acyclic: Observe → Attention → Emotion → Mood → Face, with Persistence + Memory as side-effect observers, and Behavior as a new observer that feeds back into CreatureState.

### Keeping FaceEngine as Passive Renderer

FaceEngine's current responsibilities are:

1. Reading `CreatureState` (emotion, mood, attention, engagement_drive)
2. Mapping state to visual parameters (gaze, eyelid, blink, particle effects)
3. Rendering the TFT frame buffer

If MemoryEngine influenced rendering directly, FaceEngine would need to understand memory domains, salience, recency, and dedup semantics — concerns that have nothing to do with rendering pixels.

**The Behavior Layer is the correct place for this translation.** It takes memory semantics (domain, strength, recency) and produces creature state semantics (mood, engagement, attention bias). FaceEngine consumes creature state — it never needs to know that memory exists.

This is the same pattern already used by Mood Consumption (Sprint 3B): MoodEngine publishes mood/strength to CreatureState, and FaceEngine reads those fields. MoodEngine has no knowledge of rendering. FaceEngine has no knowledge of mood arbitration rules.

### Risks of the Chosen Architecture

| Risk | Mitigation |
|------|-----------|
| Behavior Layer becomes a dumping ground for "misc behavioral logic" | Explicit scope in header comments. V1 = three deterministic rules. New rules require documented rationale. |
| Circular data flow (Behavior → CreatureState → MoodEngine → ... → Behavior) | Behavior Engine writes only fields that do not feed back into Memory or Behavior. No field written by Behavior is read by MemoryEngine. |
| Engagement drive has two writers (FaceEngine decay + Behavior override) | Behavior overrides are bounded (floor/ceiling, not absolute sets) and documented as "influence" not "control." FaceEngine remains authoritative for decay. |

### Long-Term Maintainability

**Best practices preserved:**

1. **One-way data flow** — no engine reads what another engine wrote in the same tick
2. **Testability** — `BehaviorEngine.tick()` takes a `MemorySummary`, produces state diffs. Testable with synthetic memory data.
3. **No shared mutable state** — Behavior Engine does not hold internal state beyond what `recall()` provides
4. **Deterministic rules** — same memory input always produces same behavior output
5. **Additive design** — no existing subsystem modified. Rollback = delete 2 files + remove 2 lines

Proceed with Sprint 0 immediately, then Sprint 1 as specified. The Behavior Layer is the minimum architectural addition needed to close the V2.6 gap, and it preserves all existing certified subsystems without modification.
